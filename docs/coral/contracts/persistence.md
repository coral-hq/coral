## Schema & Migration Isolation (`coral/db/`)
1. **Declarative Base**: All 22 Coral tables inherit from `CoralBase` (`coral/db/base.py`), keeping Coral `MetaData` isolated from `OmnigentBase` and `ConversationBase`.
2. **Alembic Lineage**: Coral tracks migrations in `coral_alembic_version` under `coral/db/migrations/` (`coral_0000_base` -> `coral_0001_core` -> `coral_0002_session_facade` -> `coral_0003_engine_bridge` -> `coral_0004_observations` -> `coral_0005_alerts_and_gates`).
3. **Migration Gatekeeper (`ensure_coral_schema`)**:
   - Rejects `cloudflare_d1` with `NotImplementedError`.
   - Verifies Omnigent's `alembic_version` is at head before touching any Coral table; raises `CoralSchemaOrderError` if Omnigent is unmigrated or behind head.
   - Verifies single Coral head revision and rejects database revisions newer than the running Coral build.
   - Applies Coral migrations via `alembic.command.upgrade(config, "head")` inside `query_name_scope("coral.database.run_migrations")` without ever calling `CoralBase.metadata.create_all()`.
   - Commits each revision with its version stamp in its own transaction (`transaction_per_migration`); on CockroachDB, where the runner owns the transaction, `commit_crdb_revision` commits after each revision. A failure in a later revision leaves the earlier ones applied, and a rerun continues from there.
   - Binds strictly to the operational database (`services.conversation_store.storage_location`), never `conversation_storage_location`.

## Table & Column Invariants (Contract K5)
- **Workspace Partitioning**: Every Coral table has `workspace_id` (`BigInteger`) as the leading primary-key column (`DEFAULT_WORKSPACE_ID = 0` for global singleton rows in `coral_worker_leases`).
- **Zero Foreign Keys**: Cross-entity integrity is enforced in application transactions and optimistic CAS transitions rather than database foreign keys.
- **Bounded Inline Columns**: Variable-length inline payloads use `CompressedText(16_383)` (`CAPPED_TEXT`); larger artifacts spill to `coral_blob_refs`.
- **Digests & Collation**: SHA-256 idempotency and content digests use `CHECKSUM32` (`LargeBinary(32)` / MySQL `BINARY(32)`). Case-sensitive lookup keys use `CaseSensitiveString` (`utf8mb4_bin` on MySQL).
- **Enum Storage**: Persisted enums use `SmallInteger` columns paired with explicit `CheckConstraint` definitions named `ck_coral_<table>_<column>` (a widened check may carry a `_vN` suffix, so CockroachDB can replace it in one transaction).

## Session Facade Tables (`coral_0002_session_facade`)
`coral_0002_session_facade` adds three tables and widens the run pause reasons. The stores below are synchronous; async callers use `asyncio.to_thread`. Each reserve or record is insert-if-absent: it returns the stored row, re-reads it after an `IntegrityError` from a concurrent insert, and raises a conflict when the stored row differs in any recorded field. Conflict messages name only the caller's own session, stable id or op key; the exception's `fields` lists what differs and `stored` holds the stored row for logs. Lookups that act on a session take a required `run_id` and return nothing for another run's row.

| Table | Key | Store (`coral/stores/`) | Holds |
|---|---|---|---|
| `coral_session_bindings` | `(workspace_id, session_id)`; unique `uq_coral_session_bindings_effect (workspace_id, run_id, effect_cksum)`; index `ix_coral_session_bindings_run (workspace_id, run_id, role, session_id)` | `SqlAlchemySessionBindingStore` (`session_bindings.py`, protocol `SessionBindings`, query names `coral.session_bindings.*`) | The Omnigent session of a run's anchor (`role` 1) or of one engine step slot (`role` 2): run, engine `slot_id` (`CaseSensitiveString(512)`), `slot_role` (`SLOT_ROLE` codes; decides who may commit), sha256 of the creating effect key, session generation, host, and create `progress` (`reserved` 1, `row_created` 2, `initialized` 3). Anchors have no slot id, slot role or host. |
| `coral_stable_ids` | `(workspace_id, stable_id)`; index `ix_coral_stable_ids_session (workspace_id, session_id, stable_id)` | `SqlAlchemyStableIdStore` (`stable_ids.py`, protocol `StableIds`, `coral.stable_ids.*`) | Message item ids the engine sent (`kind`: `brief` 1, `steer` 2, `nudge` 3) with `content_cksum`, the sha256 of the exact text sent (`CHECKSUM32`), recorded before the send so engine items can be told from user items. |
| `coral_workspace_op_intents` | `(workspace_id, op_key)`; index `ix_coral_workspace_op_intents_run (workspace_id, run_id, op_key)` | `SqlAlchemyWorkspaceOpIntentStore` (`workspace_op_intents.py`, protocol `WorkspaceOpIntents`, `coral.workspace_op_intents.*`) | A workspace write op (`op`: `commit` 1, `salvage` 2, `reset` 3) recorded before its first try with its host, root and the `expected_head` read then; retries get the stored HEAD back. |

- **Bindings.** An anchor's session id must be `anchor_session_id(workspace_id, run_id)` (`coral/model/ids.py`), else `reserve` raises `ValueError`; the primary key therefore holds one anchor per run on every lane. `reserve` returns the stored binding only when run, role, slot id, slot role, generation, host and, for a step, effect checksum all match; otherwise it raises `BindingConflict`. A re-keyed anchor effect for the same run adopts the stored anchor, which keeps its first effect checksum. An effect already bound to another session of the run raises `BindingConflict`. So does a second step session for one run, slot and generation (`uq_coral_session_bindings_slot_generation`, `coral_0003`); its message names the slot and generation. `list_bound_sessions(cursor=, limit=)` pages, across workspaces, the step bindings (orchestrators included) at least `row_created` of runs that are starting, running or paused. `get(workspace_id, session_id, run_id=…)` returns nothing for another run's session; a session without a binding for the run is not writable, so callers must not commit for it. `record_progress` never lowers the stored progress and raises `BindingNotFound` for an unknown session. `list_for_run` returns the anchor first.
- **Stable ids.** `record_send(…, content=…)` stores the content checksum and raises `StableIdConflict` when the id is recorded with a different run, session, effect, content checksum, kind or generation. `lookup` and `list_for_session` take `run_id` and return only that run's records; `list_for_session` returns exactly the session's ids. `content_checksum(text)` gives the digest to compare with an item found under the id before treating it as the engine's.
- **Op intents.** `reserve` raises `OpIntentConflict` when the op key is recorded for another run, op, host or root. `get(workspace_id, op_key, run_id=…)` returns nothing for another run's intent.
- **Drift pause.** `coral_runs.pause_reason` accepts `drift` (`12`, `RunPauseReason.DRIFT`). The upgrade replaces `ck_coral_runs_pause_reason` with `ck_coral_runs_pause_reason_v2` inside `batch_alter_table` (a distinct name lets CockroachDB replace the check in one transaction). The downgrade refuses offline and while any run is paused for drift, restores the old check first (the step that can still fail on data), then drops the three tables. Stop Coral servers before downgrading: it drops in-flight session state.

## Engine Bridge Schema (`coral_0003_engine_bridge`)
`coral_0003_engine_bridge` stores each run's engine log, pins the graph a run started on, and holds what the engine bridge ([`session-facade.md`](session-facade.md), "The engine bridge") needs to commit, wait and answer engine tools.

| Change | Table | Holds |
|---|---|---|
| Log kind `engine` (`22`, `LogKind.ENGINE`); check `ck_coral_run_log_kind_v2` | `coral_run_log` | One row per stored engine entry: the body is the entry's JSON, `view_patch` its patch, `actor_kind` and `actor_ref` who asked (the user who started, resumed or cancelled the run, or the calling session of an engine tool), `audit_only` set for a refused entry. Engine state is never stored: it is the fold of these rows. |
| Pause reason `auth` (`13`, `RunPauseReason.AUTH`); check `ck_coral_runs_pause_reason_v3` | `coral_runs` | A run paused because its harness could not authenticate (401). |
| Slot statuses `evaluating` (`10`) and `closing` (`11`); check `ck_coral_agent_slots_status_v2` | `coral_agent_slots` | The engine's slot states after a turn ends or a handoff arrives (`evaluating`) and while an accepted slot closes (`closing`). |
| `yaml_text` and `compiled_json` (`CAPPED_TEXT`, nullable); `yaml_ref` and `compiled_ref` become nullable; check `ck_coral_workflow_versions_content` (each artifact inline or by ref) | `coral_workflow_versions` | The graph a run is pinned to, inline. |
| `engine_config` (`CAPPED_TEXT`, nullable) | `coral_run_specs` | The engine config frozen at start; the log is always replayed with it, never with code defaults. |
| `held_since` (`BigInteger`, nullable); index `ix_coral_work_finished (kind, status, finished_at, workspace_id, id)` | `coral_work` | When the current hold of an item began; the index serves the retention purge. |
| New table, key `pk_coral_tool_replies (workspace_id, run_id, cksum)` | `coral_tool_replies` (`ToolReplyRow`) | Each engine tool reply under its call's checksum, with the run version and time it was written. |
| Unique index `uq_coral_session_bindings_slot_generation (workspace_id, run_id, slot_id, session_generation)` | `coral_session_bindings` | At most one step session per run, slot and generation. Anchors have no slot, and NULLs are distinct on every lane, so they never conflict. |

- **Upgrade.** Each check is replaced inside `batch_alter_table` under a new `_vN` name. Before any change the upgrade refuses, naming at most 10 runs, while two step sessions share a run, slot and generation.
- **Downgrade.** It refuses offline, and while any run is paused `auth`, any slot is `evaluating` or `closing`, any engine log row, version without a ref or spec with an `engine_config` exists ("Cancel and delete engine runs before downgrading"). It then restores the old checks first, drops the indexes, `coral_tool_replies` and the new columns, and restores `NOT NULL` on the refs. Stop Coral servers first: it drops stored tool replies and hold starts.
- **Pinned versions** (`SqlAlchemyWorkflowVersionStore`, `coral/stores/workflow_versions.py`, query names `coral.workflow_versions.*`). `pin` writes an immutable row whose id is `derived_id("coral-workflow-version", workflow_id, content_hash, analysis_digest)`, so a compiler or analyzer change pins a new row for new runs while running ones keep theirs; a second pin of the same graph returns the stored row. It refuses YAML or a compiled graph over the column cap (`WorkflowTooLargeError`). `load` returns `None` for an absent version; a version stored only by ref cannot be loaded. The bridge recomputes the content hash and the id on load and refuses a row that does not match them.

## Alerts and Gate Tokens (`coral_0005_alerts_and_gates`)
`coral_0005_alerts_and_gates` stores run alerts and whole engine gate tokens. What raises and resolves alerts, and the routes that read them, are in [`gates-and-inbox.md`](gates-and-inbox.md).

| Change | Table | Holds |
|---|---|---|
| New table, key `pk_coral_alerts (workspace_id, id)`; indexes `ix_coral_alerts_inbox (workspace_id, owner_user_id, status, priority, created_at, id)` and `ix_coral_alerts_subject (workspace_id, run_id, subject_id)`; checks `ck_coral_alerts_kind`, `ck_coral_alerts_priority`, `ck_coral_alerts_status` | `coral_alerts` (`AlertRow`) | One alert of a run: its derived id, the run, the owner (`String(128)`, `NULL` for the single local user) and account generation it was raised for, `kind` (`gate` 1, `question` 2, `pause` 3, `watchdog` 4, `overdue` 5, `reaction` 6, `run_completed` 7, `run_failed` 8, `run_cancelled` 9), `priority` (normal 1, low 2), the derived `subject_id` resolutions match, `status` (open 1, acked 2, resolved 3), the `AlertPayload` JSON (`CAPPED_TEXT`), `created_at`, `acked_at`, `acked_by` and `resolved_at`. |
| `token` widened from `String(64)` to `CaseSensitiveString(512)`, still `NOT NULL` | `coral_gate_visits` | The engine gate token verbatim (`<activation>:<visit_no>`); the start bounds keep it within 512 characters. The rows' first writer is the engine bridge. |

- **Upgrade.** The widening runs first, in `batch_alter_table` (`recreate="always"` on SQLite, which keeps the status check and both gate indexes), with `existing_nullable=False` so MySQL's `MODIFY` keeps `NOT NULL`. On PostgreSQL and CockroachDB it is a metadata-only type change.
- **Downgrade.** It refuses offline, and while any alert exists or any gate token is longer than 64 characters ("Delete Coral alerts and gate visits whose token is longer than 64 characters before downgrading"), checked before any DDL. It then narrows `token` back to 64 characters and drops both indexes and the table. **On CockroachDB the token stays at 512 characters:** narrowing a `STRING` validates every row, which CockroachDB does only outside a transaction and behind an experimental setting, while Coral runs each revision in one transaction. The wider column is harmless to code at `coral_0004_observations` or earlier, and a re-upgrade changes nothing. Stop Coral servers first.
- **Writes** (`apply_alert_changes`, `coral/stores/alerts.py`). `Transition.alert_raises` and `alert_resolutions` are written by `apply_transition` after the gate-visit rows, in the same transaction as the engine entry: raises first (insert when the derived id is absent, never reopened; the first draft of a repeated id wins), then resolutions (the run's open and acked rows of a subject or of a set of kinds become resolved, keeping the first `resolved_at`; they also match the same commit's raises). More than 64 raises raise `TransitionTooLarge`, and a raise for another run `ValueError`, before anything is written. A payload too large for its column is refused when the draft is built. Nested query names `coral.alerts.raise`, `coral.alerts.resolve_subject`, `coral.alerts.resolve_kinds`. `FakeRunStore` mirrors these writes.
- **Reads and ack** (`SqlAlchemyAlertStore`, query names `coral.alerts.*`). `list_inbox(workspace_id=, viewer=, after=, limit=1..100)` runs one keyset query per priority (normal, then low) on `ix_coral_alerts_inbox`, newest first, and returns the rows with the cursor `(priority, created_at, id)` of the last raw row; rows whose owner differs exactly (a collation can fold case, accents or trailing spaces) or whose generation the viewer does not prove are dropped after paging. `ack` reads the row by key, answers `not_found` for another exact owner or an unproven generation, `unchanged` for a row that is not open, `not_ackable` for an open gate or question, and otherwise updates it to acked under the same owner, status, kind and generation predicates; an update that finds nothing (a resolve won) is `unchanged`. `list_for_run` is internal: it checks no owner.
- **Generation rule.** A row with a recorded account generation is listed or acked only for a request that proves that same generation (`generation_matches`).
- **Password changes** (`carry_account_generation`, `coral/stores/registration.py`). Omnigent's rotation transaction calls Coral's registered carrier (S106), which moves every row the user owns at the old generation in the request's workspace to the new one, through the rotation's own session under the nested query name `coral.registration.carry`: `coral_runs` (finished ones too, each with a new `version`, so a commit that read the old row loses its compare-and-swap), `coral_alerts` (resolved and acked ones too) and the operational database's `coral_workflows` (none records a generation yet; the workflow definitions the routes serve live in the separate `coral.db` file, which the carrier does not reach). A re-created account's new generation moves nothing. The rotation holds the account lock while it rewrites these rows, so its size grows with the user's history until alert retention (DUR-06) bounds it. A carrier error fails the password change.

## Optimistic CAS Run Store (`coral/stores/`)
1. **`start_run`**: Supports unkeyed UUIDv4 run creation and idempotent `start_key` creation (`derived_id("coral-run", user_id, start_key)`). Re-submitting an existing `start_key` with a different `RunStartSpec` digest raises `StartKeyConflict`.
2. **`load_run_state` & `apply_transition`**:
   - Reducers load a frozen `RunState` snapshot outside write locks via `shared_read_scope()`.
   - `apply_transition` enforces batch caps (`<= 64` log entries, `<= 64` outbox work items and `<= 64` alert raises, raising `TransitionTooLarge`), locks the `coral_runs` row with `FOR UPDATE`, verifies `row.version == expected_version` (raising `RunVersionConflict` on mismatch), increments `version` and `next_log_seq`, upserts modified child rows, appends `coral_run_log` entries, inserts `outbox_work` into `coral_work` with dialect-safe conflict ignore, and marks `consumed_work_ids` as `WorkStatus.SUCCEEDED`.
   - In the same transaction it also revives `revive_work_ids` (FAILED rows of the run become PENDING with attempts 0, due now, their error, result and hold cleared), releases `release_held_codes` (PENDING rows of the run whose error code is one of those become due now, their hold cleared), and inserts `tool_reply` into `coral_tool_replies` last, so a repeated checksum raises `IntegrityError` and rolls the whole transition back.
   - `lock_timeout_s` bounds the wait: on PostgreSQL and CockroachDB the transaction first sets `SET LOCAL lock_timeout` to it and `statement_timeout` to 1.5 times it (at least 1 s). MySQL keeps its lock wait timeout and SQLite its busy timeout. Every engine bridge and decision port commit passes 10 s.
   - `read_engine_log(run_id, *, workspace_id, after_seq, max_run_version, limit)` reads a run's ENGINE rows in store `seq` order up to a run version, audit rows included; `find_tool_reply(run_id, cksum, *, workspace_id)` reads a stored reply.
3. **`commit_with_retry`**: Checks `find_receipt` at the start of every attempt before loading state or invoking `reduce_fn`, retrying `RunVersionConflict` with jittered backoff up to `max_attempts` before raising `RunContended`. It passes `lock_timeout_s` to every attempt. `commit_on_run_row` retries the same way with a reducer that sees only the run row, so a run whose spec or child rows do not decode can still be paused.

## Leased Work Queue & Worker Supervision (`coral/queue/`, `coral/workers/`, `coral/reconcile/`)
1. **Unified `coral_work` Queue (`SqlAlchemyCoralQueueStore`)**:
   - Stores signals (`1`), timers (`2`), and effects (`3`) deduplicated by `uq_coral_work_idempotency (workspace_id, run_id, idempotency_cksum)`.
   - `claim_work` locks ready `PENDING` rows (`FOR UPDATE SKIP LOCKED` on PostgreSQL, CockroachDB, and MySQL), skips the runs in `exclude_run_ids`, and reads the post-lock clock before setting `lease_expires_at` and incrementing `attempts`.
   - `renew_lease` locks the row first and rejects expired or mismatched claims so a late heartbeat never revives an expired lease.
   - `reclaim_expired_work` resets expired `CLAIMED` rows to `PENDING` without resetting `attempts` or `idempotency_cksum`.
   - **Holds.** `finish_work(..., hold=True)` re-pends a `PENDING` item without spending its attempt (`attempts - 1`, never below 0), due no sooner than 5 s from now, and sets `held_since` to the first refusal of the current hold. A normal retry keeps `held_since`; a finish to SUCCEEDED, FAILED or ABANDONED, a revive, a release and a reschedule of a finished row clear it.
   - `get_work(work_ids, *, workspace_id)` reads rows by id. `reschedule_work(draft, *, workspace_id, available_at)` inserts a SIGNAL or TIMER row if absent, re-pends a finished one with attempts 0, keeps the earlier time of a `PENDING` one and leaves a `CLAIMED` one alone; EFFECT drafts are refused. `purge_finished(kinds, finished_before, limit)` deletes finished SIGNAL and TIMER rows across workspaces, oldest first, through `ix_coral_work_finished`; EFFECT rows are never purged.
2. **Effect Execution & Fencing (`WorkDrainer`)**:
   - Abandons work items (`WorkStatus.ABANDONED`) without invoking the executor when the target run is in a terminal status (`COMPLETED`, `FAILED`, `CANCELLED`), except an effect type registered `runs_after_terminal`, or when `slot_generation` does not match the current `coral_agent_slots.session_generation`.
   - Executors with external side effects call `await ctx.ensure_lease()` before them; lease loss raises `StartupLeaseLost`. The bridge's own executors (`timer`, `run_resync`, `turn_fact`) make no external side effect: their writes are compare-and-swap commits, safe to repeat after a lost lease.
   - Every failure, and a missing executor (as retryable `executor.missing`), first asks the `hold_policy`: a delay holds the item (clamped to an hour) and calls no hook. Otherwise transient failures (`EffectFailed(retryable=True)`) reschedule with jittered exponential backoff (`1s` to `300s`) up to 8 attempts before failing terminally with `error_code="infra.transient"` and `last_error_code` in the result.
   - After this worker's finish to SUCCEEDED or FAILED commits, `on_finished` runs with the finished row; its errors are logged. An item claimed more than twice its attempt limit without settling fails as `infra.transient` (`work.attempts_exceeded`) without running again.
   - Stored and logged failure text goes through `describe_exception`: a database error is named by its type, driver class and code, never its SQL or parameters. Codes are cut to 64 characters and messages to 2,000.
3. **Leader Lease, Drain Pool & Startup Sweep (`WorkerSupervisor`, `startup_recovery_sweep`)**:
   - Acquires the singleton `coral.worker.primary` lease (`120s` TTL, `30s` renewal) in `coral_worker_leases` (`workspace_id = 0`). A renewal interval of 3/4 of the lease or more is refused. A renewal that fails or hangs is retried with backoff; when the lease cannot be confirmed before its last quarter the replica steps down and cancels its work, so it never drains on an expired lease.
   - While leader, `drain_concurrency` workers (1-64, default 4) share one claim lock and never run two items of one run at once in the process. Workers, the resync task and the renewal survive errors (logged, retried after 1 s doubling to 30 s); the end of any leader task restarts leadership.
   - On leadership acquisition, runs `startup_recovery_sweep` to reclaim expired work and keyset-scan active runs (`list_active_runs_all_workspaces`), handing each to the run reconciler and isolating per-run callback errors. When a gate republisher is set (the server sets `GateRepublisher`), it pages the open gate rows (`list_open_gates_all_workspaces`), groups each page by run (a run that straddles a page waits for the next) and hands each run's rows to the republisher in that run's scope, at most `gate_concurrency` (4) runs at once, each within `gate_timeout_s` (10 s); a failure or timeout is logged and counted for that run, and a failed listing is counted without stopping the active-run scan.
   - Every `resync_interval_s` (60 s) the resync task runs the sweep again with the reconciler and the gate republisher, which then shows only prompts this process lost. Hourly it purges finished SIGNAL and TIMER rows older than `retention_s` (24 h), at most 20 batches of 500 a tick.
   - Releases the replica lease immediately on shutdown (`stop()`).
