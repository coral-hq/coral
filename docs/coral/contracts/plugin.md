# Contract K17: Coral Server Plugin Seam

## Seam Overview
- **Omnigent module**: `omnigent/server/server_plugins.py` (`CORAL(S32)`)
- **Plugin entrypoint**: `coral.server_plugin:register` (also configurable via `server_plugins` in server config or `create_app(server_plugins=...)`)

## Registration Contract
1. `create_app(...)` resolves `server_plugins` in order:
   - explicit `server_plugins` argument (when not `None`)
   - `server_config["server_plugins"]` (when key is present)
   - `OMNIGENT_SERVER_PLUGINS` comma-separated env var (set by `coral` CLI before importing `omnigent`)
2. `load_server_plugins(plugin_specs, services)` runs synchronously during `create_app(...)` after `runner_router` is constructed:
   - imports each module, invokes `register(services) -> ServerPluginRegistration`
   - eagerly imports every module in `registration.policy_modules` and verifies `POLICY_REGISTRY` is a `list`
   - raises `ServerPluginError` on any import, attribute, validation, or registration failure (aborting boot instead of running half-enabled)
3. `registration.policy_modules` are merged into `load_registry(extra_modules=...)` so agent bundle uploads accept plugin-registered policy handlers without duplicating `policy_modules` in server config. Coral registers two: `coral.omni.policies.hygiene` (`deny_vendor_ask`) and `coral.omni.policies.guards` (the stance guards `step_roster`, `orchestrator_guard` and `deny_all_tools`, marked `internal_only`, so the policy registry route leaves them out of the list it shows).
4. `registration.routers` are appended to `all_extra_routers` and mounted **before** `_SPAStaticFiles` mounts `/`. Coral mounts three: `GET /v1/coral/info` (below), the workflow definitions under `/v1/coral`, and the workflow Inbox (`GET /v1/coral/inbox`, `POST /v1/coral/inbox/{alert_id}/ack`, [`gates-and-inbox.md`](gates-and-inbox.md)). The Inbox authenticates through the server's `services.auth_provider`, which `register()` reads directly: a services object without one fails registration instead of being taken as auth off.
5. `registration.lifespan_hooks` enter inside `lifespan` after scheduler and sandbox reaper startup, and exit in reverse order before `pull_request_refresher`, scheduler, reaper, `startup_inputs`, and `runner_router` shut down.
6. `coral_lifespan` admits one lifespan per process. On a usable operational database it first claims the process (a module-level lock and flag in `coral/omni/server/plugin.py`); a second lifespan entered while the first runs raises `RuntimeError` before it registers anything, and the first keeps its registrations. The claim is released on exit, so a later lifespan can enter again. Without one the lifespan registers and claims nothing.
7. It then builds the engine bridge (`EngineBridge`, `coral/bridge/service.py`), the bridge's thread pool (8 threads, for every bridge call: feedback, timers, turn facts, resyncs, drift pauses and gate answers), the engine tools' decision pool (4 threads), the evidence pool (4 threads) and the worker supervisor with its gate republisher; registers the `coral.evidence` tool-call observer (S105, [`evidence.md`](evidence.md)), the guards, the engine tools and the bridge's `timer` and `run_resync` executors; wires gate delivery and answers (below); wires Coral's session engine when the server's stores are present; and starts the supervisor last. The supervisor's finished items feed the bridge, its hold policy is the bridge's, and its resync task repairs each active run every minute. On exit it stops the supervisor first, then unregisters in reverse order ([`session-facade.md`](session-facade.md), "Wiring" and "The engine bridge").
8. The server config key `coral_drain_concurrency` sets how many drain workers the supervisor runs, each with at most one item of a run in flight: an integer from 1 to 64, default 4. Any other value (`0`, `65`, a boolean, a string, a float) fails the start with `ValueError` before anything is registered.
9. On a usable operational database, whether or not the session engine is wired, `coral_lifespan` also registers Coral's required-policy provider `"coral"` (S52, `omnigent/runtime/policies/required_providers.py`) and, for that provider's run-status cache, a post-commit hook on the run store; both are undone on exit. The provider's policies go ahead of every other policy for sessions bound to a run: the anchor's deny-all, or the run guard followed by the orchestrator allowlist or the step roster ([`session-facade.md`](session-facade.md), "Run protection").
10. Whether or not the session engine is wired, `coral_lifespan` registers the S106 registration carrier (`register_registration_carrier`, `omnigent/server/accounts_store.py`), so a password change moves every Coral row the owner holds at the old account generation (runs and their alerts) to the new one in its own transaction, and a carrier fault fails the password change; it is removed on exit, and with no usable operational database none is registered. It then registers the gate executors `gate_publish` and `gate_withdraw` (`gate_withdraw` runs after its run ended), then the S6b verdict handler for `coral_gate_` prompts (it reads `services.auth_provider` directly, as `register()` does), then turns on the anchor's admission of approvals, then adds the S5 observer that tracks this process's gate prompts and starts the per-process prompt sweep task. It sets `app.state.coral_gate_publisher`, `coral_gate_prompts` and `coral_alert_store`; the Inbox routes read the alert store per request and answer 404 without it. On exit the sweep stops, the observer is removed, the admission turns off, answers admitted just before get 50 ms to reach the handler (which tells them to retry), and then the handler and the executors go ([`gates-and-inbox.md`](gates-and-inbox.md)).
11. In the same place `coral_lifespan` registers Coral's mutation guard `"coral"` (S53, `omnigent/server/mutation_guards.py`; `CoralMutationGuard` in `coral/omni/server/mutation_guard.py`) over the provider's cache of found bindings, undone on exit. Mutating session and agent routes ask it after their own access checks: it refuses (409 `CONFLICT`) client changes a run relies on for sessions with a binding row (runner-only events pass only from the session's own runner), screening on the `coral.run_id` label so other sessions never read Coral's store, and edits, installs, `coral__` bundle uploads and unforced deletes of `coral__` agents ([`session-facade.md`](session-facade.md), "Run protection"). A run's anchor takes approvals while the gate admission is on.

## Coral Capability Probe & Process Tokens
- `GET /v1/coral/info` returns `200` with `{enabled, version, sub_features}` (13 keys defaulting to `false`; overrides validated against `coral_sub_features` in server config) when the Coral plugin is active, and `404` when absent.
- Coral refuses `host_sharded=True` during registration and lifespan startup.
- Hosts advertise `coral_runner:2` in their hello through Coral's tool provider (below); it is left out when `CORAL_DISABLE_HOST_ENTRY_POINTS=1`. Version 2 hosts offer the engine tools. The session facade refuses a step on a host whose live hello lacks it, `coral_runner:1` included (`session.host_unsupported`, [`session-facade.md`](session-facade.md)). The token is self-reported: a compatibility gate, not an authorization boundary.
- The token is checked only when a step is created: before any row and again before the launch. Sends and later relaunches do not check it, so a step whose host is moved back to an older Coral keeps running there. An older Coral offers no engine tools, so that step cannot hand off; its turns end without one and the nudge cap pauses the run (`rejected_calls`).

## Host Entry Points
- **`omnigent.host_workspace_ops`** (`CORAL(S40b)` in `pyproject.toml`): `coral = "coral.omni.host.ops:workspace_op_handlers"`. The host loads the group on its first `host.workspace_op` frame (`omnigent/host/workspace_ops.py`, `default_workspace_op_handlers`), never at import. Each entry point is a zero-argument callable returning `{op name: handler}`; Coral's serves `head`, `diff_stat`, `read`, `fingerprint`, `commit`, `salvage` and `reset` ([`workspace-ops.md`](workspace-ops.md)). A broken contribution is skipped with a warning, and an op offered by two contributions is served by neither. Installed metadata changes only after `uv sync`.
- **`omnigent.tool_providers`** (`CORAL(S50)` in `pyproject.toml`): `coral = "coral.omni.runner.tool_provider:tool_provider"`. Omnigent loads the group once per process on first use (`omnigent/tools/extensions.py`): the host for its hello tokens, a runner for each spec's tools and prompt text. Coral's provider offers a generated bundle the engine tools of its `params.coral.generated.stance` (`coral/tools/catalog.py`): `coral_submit_handoff` to implementers and reviewers, `coral_choose_arrow` to orchestrators, nothing to the anchor, other specs or native harnesses. The production catalog lists both tools, so the provider offers their schemas and instruction text and lists both as server-dispatched. The provider imports only the standard library, the catalog, the process map and Omnigent's extension types, never server, database or engine modules. `CORAL_DISABLE_HOST_ENTRY_POINTS` removes only the host token: the host does not forward it to runners, whose provider stays loaded, which is harmless.
- **`CORAL_DISABLE_HOST_ENTRY_POINTS=1`** makes Coral's contribution return no handlers (checked before the handler modules are imported), so every Coral op gets `unknown_op`, which the server maps to permanent `workspace.capability_unavailable`. It does not withdraw the host's `workspace_ops:1` capability: that token belongs to the Omnigent channel (S40), not to Coral.
